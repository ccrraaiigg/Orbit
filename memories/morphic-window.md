- `morphic-window` is hot-reloaded via `customElements.get('morphic-window').hotReload()`; when adding/rebinding host listeners, update hotReload cleanup too so old bound handlers are removed.
- Bug fixed 2026-06-18: the teal focus/hover tint (`:host(:hover) { background-color:#a8c8c8 }`) silently stopped working for any window that had gone through a cutout transition. `_setCutoutMode(false)` used to PIN an inline `this.style.backgroundColor = color` to "restore solid host bg". An inline background-color outranks the `:host(:hover)` shadow rule, so the tint never appeared. The maximize path hid the bug (its `_toggleMaximize` finally did `removeProperty('background-color')`), but the interactive-resize path (`_onResizePointerUp` → `_setCutoutMode(false)`) had no such cleanup, so a resized window kept a permanent inline gray bg. Fix: `_setCutoutMode(false)` now `removeProperty('background-color')` (hands control back to the stylesheet, whose `:host` #c0c0c0 equals the normal lock color) instead of pinning it. hotReload's `_render()` does NOT clear lingering host inline styles, so heal pre-existing affected windows once by `w.style.removeProperty('background-color')`.
- cmd-drag (and opt/ctrl-click) over iframe content works because each content iframe's `contentDocument` gets capture-phase modifier handlers. The window only scans its *light-DOM* iframes (`this.querySelectorAll('iframe')`). Iframes living inside a slotted component's **shadow DOM** (e.g. `<keep-viewer>`'s `.graph-frame` graph iframes) are invisible to that scan, so cmd-drag won't engage over them unless they're registered explicitly. Fix (2026-06-13): the per-iframe attach logic is exposed as static `MorphicWindow._attachModifierClickToIframe(iframe)`; components call it on their shadow iframes. The static iframe-discovery helpers (`_installArmDispatchers`, `_iframeOffsetForDoc`, `_setCmdHeld`, `_startModifierDrag`) now use shadow-aware `MorphicWindow._allIframes()` instead of `document.querySelectorAll('iframe')`.
- Arming defers `_startModifierDrag` via `setTimeout(...,0)`. Synthetic Playwright gestures fired faster than that macrotask can drop the drag (the up() lands before drag listeners attach), so cmd-drag tests are flaky unless you `waitForTimeout(~40ms)` after the threshold-crossing move. Real human drags span real time and are unaffected.
- Current resize cursor strategy for `morphic-window`: window-owned shadow DOM `.resize-hit` bands around the frame, mirrored to host/document cursor with `_setResizeCursor`. Remove stale body-level `[data-morphic-window-resize-surface]` experiments during hot reload; those were misleading for the visible cursor issue.
- DANGER: SqueakJS's own World is rendered inside a top-level `morphic-window` (100vw×100vh, position:fixed). NEVER bulk-remove `morphic-window` elements from the top doc — that detaches SqueakJS and kills the running image. To clear Snowglobe-mapped windows, iterate `Snowglobe windows` in-image and call `closeWindowWithID:` instead.
- Snowglobe (titlebar, non-chromeless) windows shrink-wrap to their slotted `<canvas>`: with no explicit host width/height, `position:absolute` block sizing tracks the canvas (which the resize-frame protocol sets via `canvas.width`/`height`). So height auto-tracks canvas resizes for free; an explicit inline width/height does NOT, and will desync if the canvas later grows (→ canvas overflows the chrome).
- Bug fixed 2026-06-16: `_clampToViewport` shrank an oversized host to the viewport by pinning `style.width/height`, but the shrink was ONE-WAY and `_onViewportResize` was a no-op unless web-side maximized. So a window clamped at reload (when the Integrated Browser panel was narrow) kept the stale width after the panel widened, overflowing its canvas. Fix: `_clampToViewport` now releases its prior clamp (tracked via `_clampAppliedW/H` + saved `_preClampW/H`, so it never clobbers a content component's intrinsic inline size) and re-measures before re-applying; `_onViewportResize` re-runs clamp for normal windows too. Pre-existing stale windows (clamped by the old code, no flags) need a one-time heal: for each non-`#embeddedSqueak` window with a direct `<canvas>` child, clear inline width/height and call `_clampToViewport`.
- REGRESSION from the above, fixed 2026-06-16: wiring `_onViewportResize → _clampToViewport` for normal windows meant that on EVERY viewport resize a canvas-backed (Snowglobe-mapped) window could get `style.width/height` pinned by the clamp. That resizes the host chrome WITHOUT going through `onResizeComplete`, so Squeak is never told, the `<canvas>` desyncs from the chrome, and the remote window appears to "keep going away." Fix: `_clampToViewport` now detects `canvasBacked = !!this.querySelector('canvas')` and for those windows clamps POSITION ONLY — it never writes `style.width/height` (sizing belongs to the remote display policy via the resize-frame protocol). The only legitimate path that resizes a Snowglobe window must call `onResizeComplete({x,y,width,height,done})` (see `_onResizePointerUp` and `caffeine-bounds-persist.js`); the clamp is not such a path.
